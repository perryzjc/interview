# PRD (产品需求文档)

## 概述

PRD (Product Requirements Document)，即产品需求文档，是产品管理过程中最常见也是最重要的交付物之一。它**详细地描述了一个产品（或一个新功能、一次迭代）要解决的问题、目标、范围、功能规格、交互逻辑、数据需求以及非功能性要求**。

PRD 的主要目的是作为**产品、设计、开发、测试等[[跨职能团队|跨职能团队]]之间沟通和协作的基准**，确保所有人对要做什么、为什么做以及怎么做有统一的理解。它将[[02 - 用户需求分析|用户需求]]和[[产品战略与规划/产品战略|产品战略]]转化为可执行的开发指令。

## PRD 的核心目的与受众

*   **目的**:
    *   清晰传达产品目标和用户价值。
    *   详细定义产品功能和行为。
    *   作为开发、设计、测试工作的依据。
    *   减少沟通歧义，确保信息同步。
    *   记录决策过程和需求变更。
*   **主要受众**:
    *   **开发团队 (Engineering)**: 理解功能逻辑、技术要求、数据接口等。
    *   **设计团队 (Design)**: 基于 PRD 进行[[交互设计]]和[[用户界面设计]]（通常 PRD 会包含或链接到设计稿/原型）。
    *   **测试团队 (QA)**: 编写[[测试用例]]，验证产品是否符合需求。
    *   **项目经理/Scrum Master**: 了解范围，协助规划和跟踪进度。
    *   **其他[[利益相关者管理|利益相关者]]**: (如运营、市场、客服) 了解即将上线的功能。

## PRD 的常见结构与内容

PRD 没有绝对标准的模板，其详细程度和结构会根据公司文化、项目复杂度、[[敏捷开发|开发流程]]（敏捷 vs 瀑布）等因素有所不同。但通常会包含以下核心部分：

1.  **引言/背景 (Introduction/Background)**
    *   **目标 (Goals)**: 本次迭代/功能要实现什么业务目标或[[OKR|OKR]]？要解决什么[[用户画像|用户]]的什么[[痛点|痛点]]？
    *   **背景 (Context)**: 为什么要做这个功能？相关的[[市场与行业分析/市场调研|市场]]或[[竞品分析|竞品]]情况？
    *   **范围 (Scope)**: 本次 PRD 包含哪些内容？不包含哪些内容 (Out of Scope)?
    *   **[[05 - 数据指标与衡量|衡量指标]] (Metrics)**: 如何衡量本次改动是否成功？（关键 [[KPI|KPI]]）
    *   **(可选) 修订历史 (Revision History)**: 记录文档的修改内容、时间和作者。
2.  **[[用户画像|用户画像]]与[[用户研究/用户场景|用户场景]] (Personas & Use Cases / Scenarios)**
    *   简要描述目标用户是谁。
    *   描述用户在哪些具体场景下会使用这些功能来完成什么任务。
3.  **[[用户研究/用户故事|用户故事]] (User Stories) / 功能列表 (Feature List)**
    *   （敏捷常用）以“作为一个 [角色], 我想要 [完成某事], 以便 [获得某种价值]”的格式描述用户需求。
    *   或者直接列出本次迭代包含的功能点。
4.  **功能详述 (Functional Specifications)**
    *   **这是 PRD 的核心部分**。
    *   对每个功能点进行详细描述：
        *   **逻辑流程 (Logic/Flow)**: 功能如何运作？涉及哪些步骤？可以使用[[设计工具/流程图|流程图]]辅助说明。
        *   **界面元素 (UI Elements)**: 页面包含哪些控件（按钮、输入框、列表等）？
        *   **交互说明 (Interaction Details)**: 用户操作（点击、滑动、输入）后系统如何响应？各种状态（正常、异常、空状态）如何展示？
        *   **数据需求 (Data Requirements)**: 需要展示哪些数据？数据来源？数据格式？需要记录哪些用户行为数据（[[数据分析与实验/数据埋点|数据埋点]]）？
        *   **异常处理 (Error Handling)**: 出现错误（如网络中断、输入无效）时如何提示和处理？
    *   **通常会配合[[设计工具/线框图|线框图 (Wireframe)]]、[[设计工具/交互原型|交互原型 (Prototype)]]或[[设计工具/视觉设计稿|视觉设计稿 (Mockup)]]一起呈现**。PRD 应引用或链接到这些设计产出物。
5.  **非功能性需求 (Non-Functional Requirements)**
    *   对产品性能、安全性、[[可用性]]、兼容性、可扩展性等方面的要求。
    *   例如：页面加载时间应小于 2 秒；需兼容主流浏览器；符合公司数据安全规范。
6.  **发布标准 (Release Criteria)**
    *   定义产品/功能可以发布的条件（例如：所有 P0 级 Bug 已修复；核心流程测试通过）。
7.  **(可选) 未来考虑 (Future Considerations)**
    *   一些本次不做但未来可能考虑的功能或优化点。
8.  **(可选) 开放问题 (Open Issues)**
    *   记录讨论中尚未解决的问题。

## 编写 PRD 的最佳实践

*   **清晰简洁**: 使用简单明确的语言，避免歧义。结构清晰，易于阅读。
*   **用户中心**: 始终围绕用户需求和价值来阐述。
*   **完整准确**: 覆盖所有必要信息，确保细节准确无误。考虑各种边界情况和异常流程。
*   **可视化**: 善用图表、流程图、线框图、原型等可视化工具辅助说明。
*   **可维护性**: 文档应易于更新。对于[[敏捷开发|敏捷]]团队，PRD 可能是个“活文档”，需要持续维护。
*   **协作与评审**: PRD 不是 PM 独自完成的，需要与设计、开发、测试等团队成员充分沟通和评审，达成共识。
*   **明确“为什么”**: 不仅要说明“做什么”，更要解释清楚“为什么做”，帮助团队理解背后的逻辑和价值。

## PRD 在敏捷开发中的演变

在[[敏捷开发|敏捷]]环境中，传统的、冗长的 PRD 可能不再适用。需求可能更多地通过[[用户研究/用户故事|用户故事]]、[[开发流程/产品待办列表|Backlog]]、[[敏捷开发#敏捷仪式|敏捷仪式]]（如计划会、评审会）和持续沟通来传递。PRD 可能演变为更轻量级的文档，或者被 [[用户研究/用户故事|用户故事]] + [[设计工具/交互原型|原型]] + [[验收标准]] (Acceptance Criteria) 的组合所替代。但其核心目的——清晰定义需求、促进沟通——依然不变。

## 总结

PRD 是产品经理将想法转化为可执行方案的关键文档，是跨团队协作的基石。编写高质量的 PRD 需要清晰的逻辑思维、对细节的关注以及良好的沟通能力。在面试中，描述你编写 PRD 的经验、思路和包含的关键要素，能体现你的专业性和执行力。
