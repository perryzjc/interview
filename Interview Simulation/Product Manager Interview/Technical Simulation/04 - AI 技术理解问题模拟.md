# AI 技术理解问题模拟

[[00 - 面试准备指南与行动计划|返回 准备指南]]

## 概述

本模拟旨在帮助你练习回答关于 AI/LLM 核心技术概念的理解性问题。面试官提出这些问题，通常不是要考察你算法实现的细节，而是要评估你作为产品经理的**技术素养 (Technical Literacy)**、对**技术能力边界的认知**以及**将技术应用于产品的思考能力**。

**练习目标**:
*   能够用**简洁、清晰、面向产品**的语言解释核心 AI/LLM 概念。
*   理解关键技术的**作用、优势和局限性**。
*   能够讨论技术选型中的**权衡 (Trade-offs)**。
*   将技术理解与**产品应用和风险管理**联系起来。
*   参考 [[PM 对 LLM 的理解深度|PM 对 LLM 的理解深度]] 把握回答的层次。

## 练习方法

1.  **阅读问题**: 理解问题考察的核心概念。
2.  **回顾笔记**: 快速回顾知识库中相关的概念笔记（点击 `[[链接]]`）。
3.  **构思回答**: 思考如何用**自己的话**，结合**产品视角**（特别是 AI 购物助手的场景）来解释。可以先列出要点。
4.  **口头练习**: 模拟向面试官解释，注意语言的**准确性**和**易懂性**。可以想象面试官是非技术背景。
5.  **关联思考**: 思考这个技术概念与其他概念（如 RAG 与幻觉、Embedding 与向量数据库）的关系。

## 模拟问题列表

> [!question]- 问题 1: LLM & Transformer 基础
**你能用简单的语言解释一下什么是[[大型语言模型 (LLM)|大型语言模型 (LLM)]]吗？以及为什么 [[Transformer 模型|Transformer]] 架构对 LLM 的发展如此重要？**
>*   **考察概念**: [[大型语言模型 (LLM)|LLM 定义]], [[Transformer 模型|Transformer 核心思想]] ([[自注意力]]), 及其对 NLP 的影响。
>*   **回答提示**:
 >   *   LLM: 强调其通过**海量数据训练**学习语言模式，能**理解和生成文本**的能力。类比为一个知识渊博但有时会“脑补”的对话者。
 >   *   Transformer: 解释其解决了传统模型处理长距离依赖和并行计算的难题，核心在于**注意力机制**（能同时关注句子所有部分的相关性）。强调其是 LLM 能力的基础。
 >   *   联系产品: 说明这些能力如何支撑 AI 助手理解用户多样化的问题并生成自然回答。

---
> [!question]- 问题 2: 模型幻觉与 RAG
**什么是[[模型幻觉 (Hallucination)|模型幻觉]]？对于我们的 AI 购物助手，这会带来什么风险？你会如何建议技术团队来缓解这个问题？**
>*   **考察概念**: [[模型幻觉 (Hallucination)|模型幻觉定义与风险]], [[检索增强生成 (RAG)|RAG 原理与作用]], [[提示工程 (Prompt Engineering)|提示工程]]。
>*   **回答提示**:
 >   *   解释幻觉（一本正经胡说八道）。
>    *   列举购物助手场景下的风险（错误价格、库存、规格、政策 -> 用户不信任、交易纠纷）。
>  *   重点介绍 **[[检索增强生成 (RAG)|RAG]]** 作为核心缓解策略：解释其工作原理（检索可信知识库 -> 作为上下文输入 LLM），强调其能提供**准确、实时**信息。
 >   *   提及其他辅助手段：[[提示工程 (Prompt Engineering)|提示工程]]（指示模型基于事实回答）、[[模型幻觉 (Hallucination)|事实核查]]、用户反馈。

>[!question]- 问题 3: RAG 的核心组件
**为了实现 [[检索增强生成 (RAG)|RAG]] 来保证购物助手回答的准确性，我们需要哪些关键技术组件？它们是如何协同工作的？**
>*   **考察概念**: [[检索增强生成 (RAG)|RAG 流程]], [[嵌入 (Embedding)|Embedding]], [[向量数据库|向量数据库]], [[相似性搜索|相似性搜索]]。
>*   **回答提示**:
 >   *   描述 RAG 的基本流程（Query -> Retrieve -> Augment -> Generate）。
>    *   解释**[[嵌入 (Embedding)|Embedding]]**的作用：将文本（用户问题、知识库文档块）转换为[[向量 (Vector)|向量]]以捕捉语义。
  >  *   解释**[[向量数据库|向量数据库]]**的作用：存储海量文档向量，并支持高效的**[[相似性搜索|相似性搜索]]**（通常是[[近似最近邻搜索 (ANN)|ANN]]）。
 >   *   说明如何通过计算查询向量与文档向量的相似度来找到相关上下文。

> [!question]- 问题 4: 开源 vs. 闭源模型选型
**如果我们考虑为 AI 购物助手选择基础 LLM，使用像 [[LLaMA 模型系列|Llama 3]] 这样的[[开源 vs 闭源模型|开源模型]]与使用像 [[GPT 模型系列|GPT-4o]] 或 [[Claude 模型系列|Claude 3]] 的 [[API (应用程序接口)|API]] 相比，各有哪些主要的优劣势？你会如何权衡？**
>*   **考察概念**: [[开源 vs 闭源模型|开源 vs 闭源对比]], [[技术选型|技术选型权衡]]。
>*   **回答提示**:
  >  *   系统性地从几个维度对比：**性能** (通用 vs. 微调后)、**成本** (API vs. 部署维护)、**控制权/定制化**、**数据隐私**、**易用性/开发速度**、**社区/生态**、**风险**。
>    *   结合 AI 购物助手的场景进行权衡：
>     *   对**数据隐私**要求高吗？（用户对话、购物数据）-> 可能倾向开源。
  >      *   需要**快速上线 MVP** 吗？-> 可能倾向 API。
 >       *   需要针对**特定商品知识**做深度定制吗？-> 可能倾向开源+[[AI & ML/微调 (Fine-tuning)|微调]]。
 >       *   团队的**技术实力和资源**如何？
 >       *   **长期成本**考量？*   强调没有绝对最优，需要根据具体阶段和战略目标做决策。

> [!question]- 问题 5: 模型评估超越 Benchmark
**除了看公开的[[基准测试 (Benchmark)|Benchmark]]分数，你会如何评估一个 LLM 是否真正适合我们的 AI 购物助手产品？**
>*   **考察概念**: [[基准测试 (Benchmark)|Benchmark 局限性]], [[模型评估]], [[数据分析与实验/A_B 测试|A/B 测试]], [[用户反馈]]。
>*   **回答提示**:
  >  *   首先承认 [[基准测试 (Benchmark)|Benchmark]] 的参考价值，但强调其局限性（无法完全模拟真实场景、可能应试、忽略实际应用指标）。
  >  *   提出更重要的评估方式：
  >      *   **领域特定测试集 (Domain-Specific Evaluation)**: 构建专门针对电商购物场景的问题集（覆盖商品咨询、比较、推荐、售后等），评估模型在这些**真实场景**下的表现（准确性、相关性、[[模型幻觉 (Hallucination)|幻觉率]]）。
 >       *   **在线 [[数据分析与实验/A_B 测试|A/B 测试]]**: 将不同模型或同一模型的不同版本部署给部分用户，直接比较它们对**核心业务指标**的影响（如[[数据分析与实验/转化率|转化率]]、[[数据分析与实验/客单价|客单价]]、用户满意度 CSAT、联系人工客服率）。这是最可靠的评估方式。
 >       *   **人工评估 (Human Evaluation)**: 请内部员工或真实用户对模型的回答质量（有用性、流畅度、安全性、语气等）进行打分。
 >       *   **[[用户研究/用户反馈|用户反馈]]分析**: 收集和分析用户对助手表现的直接反馈。
 >       *   **[[数据分析与实验/KPI|关键业务指标]]监控**: 关注助手上线后对整体业务指标的影响。
